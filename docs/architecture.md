# Architecture and decisions

## Components

| Component | Responsibility |
|---|---|
| `models.py` | Bounded Pydantic contracts, identifiers, units, shape and event validation |
| `io.py` | Explicit local CSV/WAV/PyAV/MNE import adapters |
| `synthetic.py` | Seeded signals and deterministic, separately recorded fault ground truth |
| `sync.py` | Robust shared-event affine clock estimation and same-signal audio lag utility |
| `qc.py` | Timestamp and modality-specific threshold checks |
| `engine.py` | Pure orchestration, trace summaries, hashes and correction manifest |
| `report.py` / `cli.py` | Atomic JSON and escaped HTML exports; command-line workflows |
| `api.py` | Bounded local HTTP requests, limited concurrent analysis, report history and UI hosting |
| `web/` | React/TypeScript workbench with validated report import and static-demo/local-engine modes |

## Why a modular monolith

The first bottleneck is reliable analysis, not distributed orchestration. A Python package plus a same-origin API and static frontend is easy to debug, deploy, test and run privately. Kafka, Redis, object storage and Kubernetes are not required by this release's workload. Reports use atomic local files rather than an operational database.

## Frontend modes

The static build can run on any subpath-capable static host. It loads five reports generated by the actual Python engine. When served by the local FastAPI process, a health check enables fresh synthetic analysis, Session JSON analysis and local history. A report can always be opened entirely in-browser. No remote API address is collected or stored.

The UI shares one cursor and visible time window across all traces. It uses the same correction parameters exported by the backend. Failed or absent clock estimates suppress corrected previews. Report import is schema-validated before it enters application state.

## Resource and security boundaries

Python operates on bounded in-memory recording windows. Large recordings and streaming require a future chunked API. The service is single-user and loopback-only; internet deployment would require authentication, stronger per-user quotas, isolation and a deployment security review. See `SECURITY.md`.

## Future extensions, not shipped claims

1. Disk-backed chunked readers and long-recording benchmarks.
2. Piecewise clock models and calibrated uncertainty across real devices.
3. Hardware trigger/LSL adapters and export into BIDS-compatible workflows.
4. Optional acoustic, facial or turn-taking plugins isolated from the acquisition-QC core.
5. A separately secured multi-user service if actual users need it.
